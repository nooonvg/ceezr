## الفكرة التي أزالت الحجب

الخطوة كانت محجوبة لأن حالات الاستخدام تحتاج قاعدة بيانات. الحل ليس تزييف قاعدة بيانات، بل **عزل القرار عن التنفيذ**:
`matchOrder` تقرأ عبر **منافذ** (عقود)، وتُخرج **قراراً** لا رسالةً. القرار يُختبر كاملاً بلا أي مفتاح،
والتنفيذ الحقيقي (Supabase/تلغرام) يُوصَل لاحقاً بمحوّل واحد بلا تعديل سطر في الدومين.
القرار موثَّق في `docs/adr/0004-ports-live-in-application.md`.

## سجل الإعدادات هو البوابة الوحيدة للأرقام

`parseCitySettings` هو المكان **الوحيد** الذي تدخل منه قيمة تجارية إلى الكود، ويرفض:

- **مفتاحاً ناقصاً** — يُسمّيه بالاسم، ولا يستخدم قيمة افتراضية مخفية أبداً.
- **نوعاً خاطئاً** — مهلة عرض كسرية، نصف قطر سالب، عملة فارغة، قائمة لغات فارغة أو ليست نصوصاً.
- **وزناً خارج `[0,1]`**، و**وزنين لا يجمعان 1** (`INCONSISTENT_WEIGHTS`) — حماية رياضية تُبقي النقاط في مدى قابل للتفسير.
- **صفّاً ينتمي إلى مدينة أخرى** — عزل المدن (القاعدة 0.4) مفروض حتى في القراءة.

ويتجاهل بهدوء أي مفتاح مستقبلي مجهول، فلا يسقط النظام عند إضافة مفتاح قبل نشر الكود.

## مسار `matchOrder`

```
الطلب → حالته searching؟ → إعدادات المدينة (تحقّق كامل) → دورات البثّ لم تُستنفد؟
      → عروض الطلب السابقة → من يُستبعد؟ → مرشحو المدينة → تقييم الدومين → دفعة البثّ
```

تعيد الدفعة ومهلة العرض ورقم الدورة القادمة و**أسباب استبعاد كل مرشح**، أو أحد الأخطاء:
`ORDER_NOT_FOUND`، `ORDER_NOT_SEARCHING`، `BROADCAST_ROUNDS_EXHAUSTED`، `NO_ELIGIBLE_DRIVER`،
أو خطأ إعدادات، أو `PORT_FAILURE`. **لا `throw` واحد**.
