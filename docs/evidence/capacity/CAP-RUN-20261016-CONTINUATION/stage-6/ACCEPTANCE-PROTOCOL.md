# CAP-RUN-20261016 · المرحلة 6 — بروتوكول قبول LOAD-01

> **تثبيتٌ مسبق قبل تشغيل الموجات.** كُتب هذا البروتوكول قبل تنفيذ أي موجة قبول،
> ولا يُعدَّل بعد رؤية النتائج إلا بتصريحٍ صريحٍ موثقٍ (وتُعاد كل موجةٍ متأثرة).
> التعريفاتُ والأرقامُ أدناه عقدٌ ملزمٌ لكل موجةٍ من موجات القبول.

## 1. تعريف «1,000 مستخدم متزامن» — تعريف رقمي

الحملُ يقيسُ دورةَ أعمالِ المنتجِ الكاملةَ عبرَ واجهاتِ Mini App الفعليةِ. وحدةُ
الحملِ هي **السيناريو الواحد**: راكبٌ + سائقٌ هويتانِ فريدتانِ مستقلتانِ تجريانِ
دورةَ أعمالٍ كاملةً (جلسة موقعة ← إنشاء رحلة ← إتاحة سائق ← عرض ← قبول ← دورة
رحلة حتى الاكتمال المثبت في القاعدة).

| المقياس | التعريف الرقمي |
| --- | --- |
| موجة N (تزامن السيناريوهات) | N سيناريو نشطًا في آنٍ واحدٍ (`conc=N` في PROFILE) |
| الهويات الفريدة النشطة | 2N هوية فريدة: N راكبًا + N سائقًا (هوية واحدة لكل دور، بذرٌ متصاعد لا يعاد استخدامه) |
| الجلسات المتزامنة | جلسة موقعة حقيقية لكل هوية (مبادلة `/v1/session/telegram` مرة لكل هوية ثم إعادة استخدام) |
| توزيع الأدوار | 50% ركاب / 50% سائقون |
| معدل إنشاء الرحلات | يُقاس فعليًا (السيناريوهات المكتملة/الثانية) — لا يُفترض مسبقًا |
| تحديثات Mini App | استطلاع لوح العروض كل 2 ثانية لكل سائق منتظر + تحديث موقع واحد لكل سيناريو |
| موجات القبول | 50 → 100 → 250 → 500 → 750 → 1000 سيناريو متزامنًا (أي 100 → 200 → 500 → 1000 → 1500 → 2000 هوية نشطة) |
| الإحماء | لا مرحلة إحماء: كل موجة تبدأ من مقعدٍ نظيفٍ مُثبتِ النظافة |
| نافذة الحقن | 180 ثانية لكل موجة (إيقاف إنشاء السيناريوهات بعدها حرفيًا) |
| نافذة الختام (Drain) | 180 ثانية إلزامية (`DRAIN_SEC=180` > `MATCH_WAIT_MS=120s` + دورة الرحلة) — سقفٌ صارم لا انتظارًا مفتوحًا |
| مهلة انتظار العرض/الإسناد | `MATCH_WAIT_MS=120000` |
| حامل الحمل | مولد أحادي العنوان؛ `SESSION_EXCHANGE_PER_MINUTE=6000` في بيئة المقعد (معلنةٌ في run.env) |
| موارد بيئة القياس | 2 vCPU / 8GB RAM للبوابة + القاعدة + Redis + المولد على المضيف نفسه — **قيد بيئة يوثق مع كل موجة** |

**معنى نجاح الموجة:** كل سيناريو يُحسم إما «مثبت من القاعدة» (مكتمل) أو
«مصنف فشلًا بدقة» (مرفوض/متعثر بسبب مسمى) — ولا شيء يبقى معلقًا بعد نافذة
الختام، ولا يبقى سائقٌ في حوض الإتاحة بعد التنظيف.

## 2. معايير القبول (مثبتة مسبقًا — لا تتغير بعد النتائج)

مصادرُ الحدود: `stage-6/PROTOCOL.md` (§3.1–3.5)، الجولات التشخيصية
(`diag-r5/r6`: 99.6% مثبتة عند تزامن 20)، وضماناتُ النظامِ في D8/S5 (زمن توزيع
p95 ≤ 30s). كل نسبةٍ مقامُها **كل السيناريوهات المُطلقة في الموجة** (الناجح
والمرفوض والمتعثر) — لا الناجح فقط.

### 2.1 بوابات صارمة (أي واحدة تفشل = الموجة FAIL)

| # | المعيار | الحد |
| --- | --- | --- |
| G1 | دورات مكتملة مثبتة من القاعدة | ≥ 99.0% من كل السيناريوهات |
| G2 | إسناد مزدوج (سائق ملتزم بأكثر من طلب نشط) | = 0 |
| G3 | سيناريوهات تجاوزت نافذة الختام (`close_deadline`) أو بقيت عالقة عند الإغلاق | = 0 |
| G4 | تدقيق ما بعد الموجة (`db-audit --phase=post`) | CLEAN (لا مخالفات) |
| G5 | سائقون بقوا «متاحين» في الحوض بعد الجولة | ≤ 0.5% من سيناريوهات الموجة |
| G6 | إسناد سيناريو لسائق سيناريو آخر (`assigned_to_other_driver`) | ≤ 0.5% |
| G7 | أعطال بوابة (5xx) | ≤ 0.5% من الطلبات |
| G8 | تعثر قراءة لوح العروض (`offer_board_unreadable`) | = 0 |

### 2.2 مؤشرات الأداء (تقاس وتُقارن بالحد — تجاوزها فشل موجة)

| # | المؤشر | الحد |
| --- | --- | --- |
| P1 | p95 زمن إنشاء الرحلة (`rides_create`) | ≤ 1000 ms |
| P2 | p95 زمن قبول العرض (`driver_offer_accept`) | ≤ 1000 ms |
| P3 | p95 زمن قراءة لوح العروض (`driver_offers_board`) | ≤ 1000 ms |
| P4 | p95 زمن ظهور العرض (إنشاء الطلب → رؤيته على اللوح) | ≤ 30 s |
| P5 | p95 زمن دورة السيناريو كاملة (بدء → اكتمال في القاعدة) | ≤ 120 s |
| P6 | p99 لكل من P1–P3 | ≤ 2500 ms |
| P7 | أقدم مهمة معلقة في طابور الإشعارات عند التدقيق البعدي | ≤ 120 s |
| P8 | 429 على واجهات Mini App (`api429`) | ≤ 2% من الطلبات |
| P9 | أخطاء شبكة | ≤ 1% من الطلبات |

### 2.3 الموارد والاستقرار (تُوثق لكل موجة)

- اتصالات PostgreSQL < 280 (من 300)؛ لا رفض اتصال.
- Redis: لا فشل أوامر؛ ذاكرة مستقرة (لا نموًا غير محدود).
- البوابة: لا إعادة تشغيل أو خروج غير معالج خلال الموجة (سجل الجولة يفحص).
- CPU: يُوثق الاستهلاك (قيد بيئة 2 vCPU معلن؛ الإشباع البيئي يُصنف صراحةً
  «حد بيئة» لا «نجاح منتج» — والفصل بينهما إلزامي).

## 3. إجراء الموجة الواحدة (إلزامي بترتيبه)

1. **نظافة مثبتة**: `db-audit --phase=pre` على قاعدة الموجة؛ أي بقايا من موجة
   سابقة = تنظيف أو إعادة تهيئة قبل البدء (لا تُبدأ موجة على قاعدة غير نظيفة).
2. **تثبيت الإعدادات والشيفرة**: SHA الالتزام، حالة الشجرة (نظيفة)، `run.env`،
   بيان موارد المقعد — تُكتب في `timeline.jsonl` قبل الانطلاق.
3. **تشغيل المولد**: `PROFILE='[{"name":"wave-N","sec":180,"conc":N}]'` مع
   `DRAIN_SEC=180` و`SCENARIO_DEPTH=full` و`MATCH_WAIT_MS=120000`.
4. **الانتظار حتى نهاية نافذة الختام أو تسجيل التجاوز** (المولد يسجل المآل
   والتصريف وعدد العالقين — `phase.drain_start`/`phase.end`/`phase.close_stuck`).
5. **التدقيق البعدي**: `db-audit --phase=post` — حكم CLEAN/VIOLATIONS مع تفاصيل
   كل فاشل (الطلب، عروضه، طوابعها) وفرق اللقطات قبل/بعد.
6. **مطابقة الحكم**: مقارنة نتائج الموجة بالبوابات §2.1–§2.3 بندًا بندًا.
7. **فشل موجة**: تشخيص السبب من الأدلة → إصلاح → اختبار انحدار يعيد إنتاج
   الخلل → إعادة الموجة الفاشلة وكل موجة سابقة تأثرت بالإصلاح. لا تُعدل
   البوابات لإنقاذ نتيجة.
8. **النجاح**: الانتقال للموجة التالية بنفس الإجراء. النتائج الخام لكل موجة
   تُحفظ كاملة ولا تُستبدل.

## 4. ما بعد الموجات (شرط اجتياز LOAD-01)

- إثبات تزامن فعلي: لقطة ذروة السيناريوهات النشطة ≥ N في كل موجة، وعدد
  الهويات الفريدة 2N — من أحداث المولد لا من الإعداد.
- كل البوابات أعلاه خضراء لكل الموجات الست → `LOAD-01 = PASS`.
- أي موجة تعجز البيئةُ (2 vCPU) عن تنفيذها دون إشباعٍ بيئيٍّ → تصنف `BLOCKED`
  بذكر القيد بدقة، لا FAIL للمنتج ولا PASS.

## 5. تغطية الشرح الزائفة — ما لا يُقبل دليلًا

- 2xx لا يكفي: الحكم حالةُ القاعدةِ النهائية.
- نجاح المحاكي لا يثبت نجاح Telegram الحقيقي (الفصل مُعلن).
- «لاحظت مشكلة» ليست PASS: كل بوابة بدليلٍ قابلٍ لإعادة التحقق مرتبطٍ
  بالالتزام المختبر.

## 6. تثبيتاتُ الدفعةِ السابعةِ (2026-10-18) — مُعلَنةٌ قبلَ أيِّ موجةِ قبولٍ لاحقةٍ

> تُضافُ ولا تُغيِّرُ حدًّا ولا تعريفًا: البواباتُ وحدودُها وتعريفُ التزامنِ كما في §1–§4.

- **مزيجُ الاتصالِ ثابتٌ في كلِّ موجةِ قبولٍ:** `DRIVER_SOCKET_MIX=0.7` و`RIDER_SOCKET_MIX=0.7`
  (`deploy/capacity-run/config/run.env`)، ويُسجَّلانِ في `gen.start` ويُقرآنِ فعلًا من `gen-summary`
  (`driverSocket.mix`/`riderSocket.mix` ومعهما `opened`/`joined`). الجولاتُ التشخيصيةُ وحدَها تُغيّرُهما صراحةً.
- **نزاهةُ المقعدِ قبلَ الحقنِ (تُجهِضُ الموجةَ عندَ الفشلِ):** `MOCK PREFLIGHT` (رموزُ البوتينِ مُعرَّفةٌ
  ومختلفةٌ، و`unknown_token` لقطةٌ قبليةٌ) و`SIGNAL PREFLIGHT` (مسارا الإشارةِ الداخليةِ يردّانِ 401 بلا سرٍّ لا 503).
  وبوابةُ `EGRESS-CLASSIFIED` في التقريرِ: `unknown +0` شرطٌ.
- **قاعدةٌ نظيفةٌ لكلِّ موجةٍ:** نسخٌ من قالبٍ مُهاجَرٍ بالكاملِ + بذرةُ المقعدِ (`config/seat-seed.sql`)
  ثم تفريغُ Redis وإعادةُ تشغيلِ البوابةِ — تراكمُ r1–r10 أبطأَ المطابقةَ ~2× فأفسدَ المقارنةَ.
- **مولّدٌ يطابقُ العميلَ الحقيقيَّ:** مقبسُ السائقِ يرسلُ `offers:join` ومقبسُ الراكبِ `trip:join` عندَ
  كلِّ اتصالٍ، وإقرارُ الراكبِ بعدَ قراءةِ الأحداثِ، والبقاءُ بعدَ الاكتمالِ (`RIDER_LINGER_MS=20000`) خارجَ خانةِ التزامنِ.
- **فصلُ القنواتِ في التدقيقِ:** `riderTripChannel` في `db-audit-post.json` يفصلُ إيصالَ Mini App
  (`miniappAck`) عن قبولِ Telegram API (`telegram`) عن المعلّقِ، ويعدُّ الإيصالاتِ المكرّرةَ (يجبُ صفرًا)
  والإقرارَ المتأخرَ بعدَ تيليجرامَ. الإشارةُ (`socket.emit`) لا تُعدُّ تسليمًا في أيِّ عدٍّ.
